# WP2 — Reuse Auth State

- **Date:** 2026-10-31
- **Branch:** `wp2/reuse-auth-state`
- **Base:** `main` at `e74a82d` (WP1 merged)
- **Nature:** auth refactor. No assertion, timeout, retry, test-count, or snapshot change.

## Context

WP0 found that the repository already had an auth setup project, a storage-state file, and an authenticated dashboard test. WP1 left the remaining auth problems in place:

- `tests/auth.setup.ts` threw when `AUTH_EMAIL`/`AUTH_PASSWORD` were absent, which made its own fallback unreachable. CI masked this by supplying synthetic credentials.
- The full run still performed **5 successful UI logins + 1 invalid submission**: setup, both cross-layer tests, the UI create test, and the visual editor test.
- `tests/ui/dashboard.spec.ts` existed but was not run in CI.
- `npm run test:ui` ran only `ui-functional.spec.ts`, so its name was misleading.
- Cross-layer tests use their own synthetic users, so the shared setup user is the wrong identity for them.
- The public API replaces the user's token on every login. Cleanup already had to log in again before deleting.

## Options considered

### 1. Use the shared `storageState` for every authenticated test

Cheapest option: setup writes one state file and every test reuses it. Rejected because the cross-layer and visual tests create data as their own users. Acting as the setup user would change what those tests verify and would couple their data to one shared identity.

### 2. Keep UI logins and only add the dashboard to CI

Rejected. It would bring the dashboard into CI but leave the WP2 goal unmet: non-login tests would still submit the login form.

### 3. Per-test UI login in `beforeEach`

Rejected. Same cost as today, with less explicit ownership than a fixture.

### 4. Per-test API token injection — chosen for data-owning tests

The test user is created by the existing `user` fixture. A new `authenticatedPage` fixture injects that user's JWT into `localStorage` before the first navigation. The app reads the token before its own scripts run, so no login form is submitted. The token is fresh per test and the identity matches the test's data.

### 5. Worker-scoped auth

Deferred to WP3/WP4. It would reduce setup calls, but it shares a mutable identity across tests and becomes unsafe as workers rise.

### 6. API-built storage state vs one UI login in setup

The setup project can either submit the login form once and capture the resulting state, or build the state from an API token. The API-built option is faster and removes the last non-test UI login. It relies on the app's localStorage key. The existing saved state shows the app stores only `jwtToken` and no cookies, so the key is centralized in `tests/auth-storage.ts`. If the app ever changes that contract, setup and the authenticated dashboard fail visibly and the key must be updated. The fallback is to keep one UI login in setup, which would leave two successful UI logins instead of one.

## Decision

### Auth modes

| Mode | Used by | Reason |
| --- | --- | --- |
| Shared `storageState` | `dashboard.spec.ts` | One read-only identity; no per-test data ownership. State is regenerated by setup on every run. |
| Per-test API token injection | Cross-layer tests, visual editor test | Each test owns its user and article; the shared setup user would be the wrong identity. |
| Per-test UI login | UI create test, invalid-login test | The login flow itself is under test. |
| Worker-scoped auth | None | Shared identity and mutable token; deferred to WP3/WP4. |

### Implementation choices

- `tests/auth-storage.ts` owns `JWT_STORAGE_KEY = "jwtToken"` and `buildStorageState(baseURL, token)`.
- `tests/auth.setup.ts` uses `request`, not `page`. It no longer throws when `AUTH_*` are absent; it creates a session-local user instead. It still throws on a non-401 API error.
- `fixtures/test-base.ts` adds `authenticatedPage`, which depends on `page` and `user` and sets `localStorage.jwtToken` through `page.addInitScript`.
- Cross-layer tests use `authenticatedPage` and keep `test.use({ storageState: empty })` so the setup user cannot leak in. Test 2 reads the article with `user.token` because no UI login rotated it.
- The visual editor test uses the same fixture and page objects. The snapshot is unchanged.
- `npm run test:ui` now runs `tests/ui` (functional + dashboard). `test:ui:functional` keeps the old focused command.
- CI passes `AUTH_EMAIL`/`AUTH_PASSWORD` through from repository variables without synthetic defaults, so the absent-variable fallback is exercised.
- The expected `405` user-deletion warning is unchanged. Cleanup semantics belong to WP3.

### Why the token-rotation workaround stays in the article fixture

The article fixture still logs in before deleting. That is a safety net for any future test that does log in through the UI. In WP2's cross-layer tests no UI login occurs, so `user.token` remains valid for the API read; the fixture's cleanup login is still correct because login rotates the token.

### Expired state

- Setup is a project dependency, so `playwright/.auth/user.json` is regenerated on every Playwright invocation.
- The file is gitignored (`git check-ignore` confirms).
- Dashboard is the only consumer of the shared state. If the token expires mid-run, the test fails visibly; there is no retry.
- Per-test tokens are created per test, so they do not share an expiry window.

## Trade-offs

- The app-specific `jwtToken` key is now a named constant. This is a deliberate, visible coupling to the RealWorld UI storage contract.
- The setup user still cannot be deleted (the API returns `405`), so every run leaves one synthetic setup user on the public environment.
- The visual editor test now uses the `user` fixture, so it also logs the expected `405` cleanup warning.
- The public app/API remains intermittently inconsistent. WP2 does not add retries, sleeps, or timeout increases.
